| 项目 | 内容 |
|---|---|

| 文档版本 | v0.1 |

| 产品形态 | Web / H5 单页应用（响应式，兼容移动端浏览器） |

## 1. 项目背景

### 1.1 背景

市面上讲解中国艺术史的内容（图书、纪录片、博物馆导览、通识课程）普遍采用**时间线叙事**：按朝代顺序讲画家、画派、代表作。这种叙事有两个结构性缺陷：

1. **看不到空间维度**。学习者能背出「元四家」「吴门四家」，却说不出他们分别在哪个城市活动，无法理解风格差异背后的地理与经济成因。
2. **看不到因果关系**。为什么南宋山水从全景变成「一角半边」？为什么文人画在元代江南而非大都崛起？脱离地理与政治版图，这类问题只能被归因于「审美趣味变化」，而真实的驱动力是都城迁移、经济重心南移、赞助人结构变化。

### 1.2 机会

百度地图开放平台提供了成熟的 WebGL 地图渲染、个性化底图样式、POI 检索与路线规划能力，且 JSAPI 免费、无调用次数限制。这让我们可以用极低的成本，把「时间线叙事」升级为**「时间 × 空间」双轴叙事**。

### 1.3 已有资产

本项目是「中国艺术史小程序」的内容延伸，可复用已有的朝代、画家、作品内容沉淀，避免从零构建知识体系。

## 2. 产品定位与目标

### 2.1 一句话定位

> 一张会随时间变化的中国艺术地图，让人 3 分钟看懂「中国美术的中心为什么一路往南走」。

### 2.2 核心观点（产品的护城河）

本产品不是 POI 的堆砌，而是承载一个明确的史学观点。所有数据组织与视觉叙事都围绕这条主线展开：

**长安（唐）→ 分裂南移（五代）→ 汴京集权（北宋）→ 临安收缩（南宋）→ 江南文人化（元）→ 苏州商业化（明）→ 京·扬·沪三分（清）**

背后贯穿三条城市逻辑：

| 逻辑 | 说明 | 典型朝代/城市 |
|---|---|---|
| **政治逻辑** | 艺术中心 = 首都，由宫廷财力与画院制度决定 | 唐·长安、北宋·汴京、清·北京 |
| **经济逻辑** | 艺术中心 = 富庶商业城市，由市场与收藏家决定 | 明·苏州、清·扬州 |
| **文化逻辑** | 艺术中心 = 文人聚集地，由士人网络与师承决定 | 元·江南、明·南京 |

### 2.3 产品目标

| 目标层级 | 描述 | 衡量方式 |
|---|---|---|
| 用户价值 | 建立中国艺术史的空间认知框架，理解风格变迁的地理成因 | 用户能复述「中心南移」这条主线 |
| 传播价值 | 具备自传播性的可视化作品，为公众号内容矩阵引流 | 分享率、人均停留时长 |
| 资产价值 | 成为「中国艺术史小程序」的内容入口与差异化标签 | 跨产品跳转率 |

## 3. 目标用户与场景

### 3.1 目标用户

| 用户群 | 特征 | 核心诉求 |
|---|---|---|
| **艺术/人文爱好者**（主力） | 25–40 岁，看过艺术史通识内容，去过博物馆 | 想建立体系化认知，而不只是记知识点 |
| **学生与教育场景** | 中学生、艺术类考生、通识课学生 | 需要直观、可记忆的辅助材料 |
| **文旅人群** | 计划做博物馆/古迹主题旅行 | 想把历史知识转成可执行的行程 |
| **内容创作者** | 需要可视化素材做二次传播 | 截图/分享素材的可用性 |

### 3.2 核心使用场景

1. **碎片化浏览**：通勤时打开，拖一遍时间轴，几分钟内获得完整认知框架。
2. **深度学习**：锁定某朝代，逐城点开看画派、画家、代表作，形成知识树。
3. **出行转化**（P1）：看到「南宋的临安」，顺手查今天杭州能看什么展、怎么走。
4. **社交分享**：生成「我在南宋的临安」式海报分享到社交平台。

## 4. 需求范围

### 4.1 MVP（v0.1）范围

- 朝代时间轴（7 档：唐 / 五代 / 北宋 / 南宋 / 元 / 明 / 清）
- 地图点位可视化（城市 × 画派，气泡半径 = 活跃度权重，颜色 = 画派类型）
- 艺术中心迁移轨迹线（随朝代推进生长）
- 点位详情面板（时代背景 + 该地画派 + 代表画家）
- 图例（四种画派类型配色说明）

### 4.2 明确不做（本版本）

| 不做项 | 原因 |
|---|---|
| 用户系统 / 登录 / 收藏 | 不产生核心价值，增加开发与合规成本 |
| AI 生成讲解 | v0.1 使用人工撰写文案保证质量与准确性，v1 再引入 |
| 作品高清图库 | 版权风险高（详见第 9 节），v0.1 以文字与色块示意为主 |
| 全景地图 / 室内地图 / 鹰眼轨迹 | 与核心叙事无关，属于过度设计 |
| 后端服务与数据库 | 数据量小，静态 JSON 随包发布即可 |

## 5. 功能需求

### 5.1 功能清单

| 编号 | 优先级 | 模块 | 功能 | 验收标准 |
|---|---|---|---|---|
| F01 | P0 | 地图 | 地图容器初始化 | 加载百度地图 JSAPI GL，默认视野覆盖中国全境，初始中心点 (104.0, 35.0)，缩放级别 5 |
| F02 | P0 | 地图 | 个性化底图样式 | 使用自定义样式：隐藏 POI 冗余标注、路网弱化、底色偏绢帛/水墨，视觉上呈现「古地图」质感 |
| F03 | P0 | 时间轴 | 朝代切换 | 底部 7 档朝代按钮，支持点击切换；支持键盘 ← → 切换；移动端支持横向滑动 |
| F04 | P0 | 可视化 | 艺术中心气泡 | 按当前朝代渲染城市点位，半径 = `7 + weight × 20`（px），透明度 = `0.28 + weight × 0.42` |
| F05 | P0 | 可视化 | 切换过渡动画 | 朝代切换时气泡半径与透明度使用 CSS transition（0.55s，cubic-bezier(.4,0,.2,1)），城市标签同步高亮/淡化 |
| F06 | P0 | 可视化 | 迁移轨迹线 | 按主中心顺序绘制虚线，随当前朝代推进而生长；唐（仅起点）不绘制轨迹 |
| F07 | P0 | 图例 | 画派类型图例 | 常驻显示四种类型配色：宫廷（朱砂）/ 文人（石青）/ 宗教（赭石）/ 市民（石绿） |
| F08 | P0 | 详情 | 点位详情面板 | 点击气泡展示：朝代名、起止年份、时代背景叙事（80–120 字）、该地画派、代表画家 2–3 位 |
| F09 | P0 | 详情 | 侧栏信息区 | 固定展示当前朝代：名称、年份区间、叙事文案、按权重排序的中心列表 |
| F10 | P1 | 检索 | 画家索引 | 点位详情内可展开该地画家列表，含生卒年、代表作、收藏机构 |
| F11 | P1 | 地图 | 「今天怎么走」行程模式 | 调用 POI 检索获取当前城市博物馆/古迹，支持路线规划，把历史路线映射为今日可执行行程 |
| F12 | P1 | 传播 | 分享海报 | 生成含朝代、城市、一句叙事的分享卡片，支持长按保存 |
| F13 | P2 | AI | AI 讲解 | 点击点位生成口语化讲解词，支持「讲得再细一点」「用给孩子听的口吻」等指令 |
| F14 | P2 | 地图 | 附近展览 | 基于定位 + POI 检索，推荐周边在展的书画类展览 |

### 5.2 核心交互流程

**主流程（浏览）**

```
进入页面
  → 默认定位到「唐」
  → 地图渲染长安气泡 + 侧栏展示唐代叙事
  → 用户点击/拖动时间轴
  → 气泡按新朝代数据过渡变化，轨迹线生长
  → 侧栏叙事与中心列表同步更新
```

**次流程（深挖）**

```
用户点击某个城市气泡
  → 弹出详情面板（朝代背景 + 画派 + 代表画家）
  → （P1）展开画家索引 → 查看代表作
  → （P1）点击「今天怎么走」→ POI 检索 + 路线规划
```

### 5.3 画派类型定义

| 类型 | 配色 | 定义 | 示例 |
|---|---|---|---|
| 宫廷 | 朱砂 `#a8322d` | 由朝廷/画院制度供养，服务于政治与礼制 | 翰林图画院、画院体 |
| 文人 | 石青 `#3a6b8c` | 士人业余创作，强调写心与笔墨趣味 | 元四家、吴门画派 |
| 宗教 | 赭石 `#9c6b3f` | 服务于寺观石窟的壁画与造像 | 敦煌壁画、永乐宫壁画 |
| 市民 | 石绿 `#5c7f5e` | 由商业市场与市民/盐商赞助驱动 | 扬州八怪、海上画派 |

## 6. 数据需求

### 6.1 数据规模（MVP）

| 实体 | 数量 | 说明 |
|---|---|---|
| 朝代 | 7 | 唐、五代、北宋、南宋、元、明、清 |
| 城市 | 12 | 见附录 B |
| 艺术中心（朝代 × 城市） | 约 30 | 含权重与类型 |
| 画家 | 约 30 | 每朝代 3–6 位 |
| 作品 | 约 60 | 每位画家 1–3 件 |

### 6.2 数据模型

```json
{
  "dynasties": [
    {
      "id": "song_s",
      "name": "南宋",
      "start": 1127,
      "end": 1279,
      "narrative": "偏安临安，院体山水的构图从全景收缩为「一角半边」。政治版图的收缩，被画家直白地写进了画面的留白里。"
    }
  ],
  "places": [
    {
      "id": "hangzhou",
      "name": "杭州",
      "lng": 120.15,
      "lat": 30.27,
      "coordSystem": "BD09"
    }
  ],
  "centers": [
    {
      "dynasty": "song_s",
      "place": "hangzhou",
      "weight": 1.0,
      "type": "宫廷",
      "note": "绍兴画院·马远夏圭"
    }
  ],
  "figures": [
    {
      "name": "马远",
      "birth": 1140,
      "death": 1225,
      "place": "hangzhou",
      "dynasty": "song_s",
      "works": [
        { "title": "踏歌图", "collection": "故宫博物院" }
      ]
    }
  ]
}
```

### 6.3 字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `weight` | float | 是 | 活跃度权重 0–1，决定气泡半径与透明度，同一朝代内相对可比 |
| `type` | enum | 是 | 宫廷 / 文人 / 宗教 / 市民，决定气泡配色 |
| `coordSystem` | string | 是 | 必须为 `BD09`；原始 WGS-84 坐标须经转换后入库 |
| `narrative` | string | 是 | 朝代叙事文案，80–120 字，需体现地理成因 |

### 6.4 数据生产建议

先在飞书多维表格中按上述结构录入，再导出 JSON。相比手写 JSON，表格录入效率更高且便于协作校对。

## 7. 技术架构

### 7.1 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 构建 | Vite | 冷启动快，配置简单 |
| 前端框架 | React + TypeScript | 时间轴为全局状态，组件化管理更清晰；类型约束可降低数据录入错误 |
| 状态管理 | React `useState`（MVP）/ Zustand（如需扩展） | 核心状态仅 `currentDynasty` 一个 |
| 地图 | 百度地图 JSAPI GL v1.0 | WebGL 渲染，支持百万级点、个性化底图样式、自定义图层 |
| 数据 | 静态 JSON，随包发布 | 数据量小（< 200KB），无需后端与数据库 |
| 部署 | 腾讯云 EdgeOne Pages / Vercel | 静态托管；国内访问速度前者更优 |
| 开发提效 | 百度地图 Docs MCP | 在 AI 编程工具中直接查询 API 文档，避免模型凭记忆写错参数与版本 |

```

```

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 首屏加载 ≤ 2s（4G 网络）；朝代切换动画帧率 ≥ 50fps；点位数量级 < 100，无需聚合 |

| 埋点 | PV/UV、朝代切换次数分布、点位点击率、平均停留时长、分享点击率 |

## 9. 风险与限制

| 风险 | 影响 | 应对措施 |
|---|---|---|
| **坐标系偏差** | 百度使用 BD-09，维基百科/Google 来源为 WGS-84，直接使用会偏移数百米，城市级可视化肉眼可见 | 数据入库前统一走坐标转换接口；JSON 中以 `coordSystem` 字段标注，加载时校验 |
| **AK 盗用** | Web 端 AK 必然暴露在源码中，被他人盗用会刷爆配额 | 控制台必须配置 Referer 白名单；严禁将服务端 AK 写入前端；日调用量异常时告警 |
| **图片版权** | 文物高清图随意爬取存在侵权风险 | v0.1 不使用高清图，仅文字 + 色块示意；后续如需图片，优先采用故宫 Open Data、国博开放数据等已授权来源 |
| **史实准确性** | 权重与类型为主观赋值，可能被质疑 | 数据附录中标注依据来源；文案措辞使用「活跃度」而非绝对量化的「数量」；v1 增加「数据来源」说明入口 |
| **配额限制** | JSAPI 免费无次数限制，但 Web 服务 API / MCP 走服务端 AK 配额 | MVP 阶段为纯前端渲染，不消耗服务端配额；P1 的 POI 检索需评估调用量 |

## 12. 待确认问题

1. **产品命名**：是否沿用「可走的艺术史」，或另起更利于传播的名称？
2. **图片策略**：v0.1 是否接受「纯文字 + 色块」方案，还是必须引入作品图？若必须，版权来源如何确定？
3. **与小程序的关系**：本产品作为独立 Web 产品，还是作为小程序的 H5 嵌入页？影响分享链路与技术选型。
4. **是否引入 AI 讲解**：若 v1 引入，使用哪个模型与成本控制方式？
5. **商业化**：定位为个人作品集 / 内容引流工具，还是后续考虑付费课程转化？影响功能取舍。
